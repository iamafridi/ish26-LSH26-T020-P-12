# ADR 0001 — Data Model & Application Layering

**Status:** Accepted
**Date:** 2026-08-14
**Phase:** 0 (P0-T004)
**Owner:** Architect

## Context

TAMANNA TRADERS is a CNF (Clearing & Forwarding) agent running a single-tenant back office
on MySQL 8 / Prisma / Next.js 15. The data model must capture every money movement the
business records — jobs, bills, receipts, advances, expenses and loans — with exactness,
because the system's entire value is that the owner can trust its balances. Two constraints
govern every decision below:

1. Money is **never** a binary floating-point number (plan.md §6.6). Rounding drift destroys
   trust.
2. Business dates are **timezone-free** (`DATE`); audit timestamps are UTC (`DATETIME`).
   Mixing them is the source of the classic "yesterday's bill" bugs (plan.md §6.6, §9.3).

## Decisions

### 1. Layering (plan.md §12.2)

UI → Server Actions / Route Handlers (auth check + Zod only) → Services (`src/server/services/`)
→ Prisma (`src/server/db.ts`). No Prisma import outside the service layer — enforced
mechanically by an ESLint `no-restricted-imports` rule scoped to `src/app/**` and
`src/components/**`. Components and route handlers call a service; the service owns the
query and the transaction. This keeps an agent-built codebase coherent: the boundary is
lint-enforced, not review-enforced.

### 2. Prisma 7 mechanics (not a choice, a fact of the installed version)

- Connection URLs live in `prisma.config.ts`, **not** `schema.prisma` (Prisma 7 rejects
  `url` in the schema with P1012).
- The client is built with `@prisma/adapter-mariadb` (Prisma's MySQL driver adapter) in
  `src/server/db.ts`.
- Generator is `prisma-client` emitting TypeScript to `src/generated/prisma` (gitignored,
  regenerated by `postinstall` and `build`).
- Seed runs from `prisma.config.ts` → `tsx --env-file=.env prisma/seed.ts`.

### 3. Money representation

Every money column is `Decimal @db.Decimal(18, 2)`. In application code it is Prisma
`Decimal` (decimal.js under the hood). `src/server/db.ts` sets `decimalAsNumber: false`
and `bigIntAsNumber: false` so the driver hands DECIMAL back as a string — a JS float would
reintroduce R2 (plan.md §20) below anything the lint rule can see. Commission percentages
and FX rates are `Decimal(18, 4)` — they are rates, not money, and need more precision than
2dp (a rate of `1.0850` must not be silently truncated).

### 4. Identity & audit columns

Every table carries `id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY`, `created_at`,
`updated_at`, `created_by`, `updated_by`. `created_by` / `updated_by` are `BIGINT` columns
holding a `users.id`; they are **not** Prisma relations so a user row can never block a
deletion chain, and `users` is soft-deleted anyway (`is_active`). The authoritative
user-action trail is `audit_log`, which IS a real FK to `users`.

### 5. Soft delete only

No hard delete on any transactional or master row. Active state is `is_active`
(master data) or a `status` enum (operational data). All relations are
`onDelete: Restrict` — a referenced row can never be silently cascaded away. This is
plan.md §9.3 and the DB Engineer's integrity contract.

### 6. Business dates vs audit timestamps

Business dates (`bill_date`, `expense_date`, `receipt_date`, `advance_date`, `c_date`,
`taken_date`, `joining_date`, `invoice_date`, `payment_date`) are `DateTime @db.Date` — a
MySQL `DATE`, no time, no timezone. Audit stamps (`created_at`, `updated_at`, `issued_at`,
`cancelled_at`, `adjusted_on`, `last_login_at`, `expires_at`) are `DateTime @db.DateTime(3)`
stored UTC. Display timezone is `Asia/Dhaka` (set in `vitest.config.ts` and `.env`).

### 7. Bill-line snapshots

`bill_lines` carries `label_snapshot`, `value_type_snapshot`, `revenue_class_snapshot` —
all `NOT NULL`. A bill must render correctly even if every billing parameter is later
renamed, re-typed or deactivated (plan.md §M3 rule, §9.3, R5). `parameter_id` on a line is
nullable: the line is self-sufficient; the parameter is a reference back for analysis, not
a rendering dependency.

### 8. Billing parameters — typed catalogue

`value_type` and `revenue_class` are fixed Prisma enums (AMOUNT / TEXT / COMMISSION /
ADVANCE_ADJUSTMENT / PERCENT_OF_BASE and COMMISSION / SERVICE_CHARGE / REIMBURSEMENT /
ADJUSTMENT / NARRATIVE). Only the **catalogue** is user-extensible — the type system is not
(plan.md §M3, R6). `default_value` is a nullable `Decimal(18,2)`; a blank default is valid
and means the operator fills it in at bill time. A separate `default_text_value` holds the
TEXT default so money stays typed; the UI value-type picker shows only the relevant field.

### 9. Bill numbering enforces at the database

`bills.bill_no` is `UNIQUE` and `@@unique([bill_year, bill_seq])` — the database is the
final arbiter against collision even if application locking (ADR 0002) is wrong. Drafts
have NULL number, year and sequence (assign-on-issue, plan.md §7.2, A4).

### 10. Advance engine constraints

`advance_adjustments.amount` is `Decimal(18,2)`; positivity (`> 0`) and the §8.4 invariant
`Σ advances − Σ adjustments ≥ 0` are enforced in the service layer and asserted by the
integrity job — MySQL `CHECK` constraints on this would duplicate logic and Prisma does not
emit them for MySQL. `advance_adjustments.bill_line_id` is nullable (a reversal can target
a bill without a single line in edge cases, and ADR 0004 specifies the exact wiring).

### 11. Expense table is one table driven by category kind

A single `expenses` table with nullable `staff_id`, `client_id`, `job_id` and payment
instrument fields. `is_reimbursable` and `affects_pl` are **derived from the category's
kind** and stored denormalised for cheap reporting — never taken from user input
(plan.md §M9). `loan_payment_id` links the auto-posted expense row back to the loan
payment that created it (plan.md §M10) and is nullable.

### 12. Indexes from day one

The plan.md §9.2 index set is declared `@@index` in the schema, so the first migration
creates them. Reports are the hot path; retrofitting indexes after data grows is far more
disruptive. DB Engineer verifies each report query with `EXPLAIN` (plan.md §9.2).

## Consequences

- Every later service can assume: money is `Decimal`, dates are `DATE`, IDs are `BigInt`,
  nothing is hard-deleted, every mutation has an audit story, and bills are immutable once
  snapshotted + issued.
- Writing the schema and generating the client regenerates `src/generated/prisma` — a fresh
  clone must run `pnpm install` (postinstall) before compiling.
- Trade type lives on the **job** and on the **bill**, never on the client (plan.md §M2) —
  one client can do both import and export jobs.
