# Operations Runbook — Scheduled Jobs

**Audience:** whoever administers the VPS that runs TAMANNA TRADERS CNF Back Office.
**Scope:** the two jobs that run on a timer — the nightly **backup** and the weekly
**database integrity check** — plus what to do when either of them reports a problem.

Provisioning the server is `docs/deployment.md`. Backup contents, retention and the
restore drill are `docs/backup.md`. This file is about *the schedule and the alarms*.

| Job                  | When (Asia/Dhaka)      | Runs                       | Alarm surface                                  |
| -------------------- | ---------------------- | -------------------------- | ---------------------------------------------- |
| Backup + off-server  | 02:00 every night      | `scripts/backup.sh`        | cron mail, `/var/log/cnf/backup.log`, exit code |
| Integrity check      | 02:30 every Monday     | `scripts/integrity-check.ts` | Admin dashboard, `/var/log/cnf/integrity.log`, cron mail |

Both jobs assume the working directory is the application root
(`/var/www/cnf-back-office`) — they read `.env` from there. Every crontab line below
starts with `cd`, and that `cd` is not optional.

---

## 1. One-time setup

Do this once, as root, before installing the crontab.

```bash
# Log directory owned by the application user.
sudo install -d -o cnf -g cnf -m 0750 /var/log/cnf

# Runtime state directory inside the app (holds the integrity status file).
sudo -u cnf mkdir -p /var/www/cnf-back-office/.data

# Where cron mail should go. Put a real mailbox here or the alarms go nowhere.
sudo -u cnf crontab -l   # check what is already scheduled
```

`.data/` holds runtime state only. It is regenerated by the job, it is **not** part of
the deploy, and it must stay out of version control — confirm it is listed in
`.gitignore`.

Find the absolute path to `pnpm` on this server; cron runs with a minimal `PATH`:

```bash
command -v pnpm     # e.g. /usr/local/bin/pnpm — use this in the crontab
command -v node     # e.g. /usr/bin/node
```

## 2. The crontab

Install as the application user:

```bash
sudo crontab -u cnf -e
```

```cron
# ---------------------------------------------------------------------------
# TAMANNA TRADERS CNF Back Office — scheduled jobs.
# Times are Asia/Dhaka (no DST), stated explicitly so a server on UTC still
# runs the backup at 2 a.m. local.
# ---------------------------------------------------------------------------
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin
CRON_TZ=Asia/Dhaka
MAILTO=owner@example.com

# 02:00 nightly — full backup set (database + uploads) and the off-server copy.
0 2 * * *  cd /var/www/cnf-back-office && bash scripts/backup.sh >> /var/log/cnf/backup.log 2>&1

# 02:30 Mondays — weekly database integrity check (plan.md §16).
30 2 * * 1  cd /var/www/cnf-back-office && mkdir -p .data && INTEGRITY_LOG=/var/log/cnf/integrity.log INTEGRITY_STATUS_FILE=/var/www/cnf-back-office/.data/integrity-status.json /usr/local/bin/pnpm --silent db:integrity --quiet >> /var/log/cnf/integrity-cron.log 2>&1
```

Notes on that second line, all of which matter:

- **02:30, not 02:00.** The backup starts at 02:00 and holds a lock; the integrity check
  reads the same database. Half an hour apart keeps them from competing for I/O.
- **`--quiet`** prints only breaches, so a healthy week produces no cron mail at all and
  a bad week produces mail you cannot miss. The log file gets its one line either way.
- **Flags go straight after the script name** — `pnpm db:integrity --quiet`, with no `--`
  separator (pnpm 11 would forward the `--` itself; the script ignores it if you type it
  out of habit). If `pnpm` is not on cron's `PATH`, use the equivalent direct form:

  ```cron
  30 2 * * 1  cd /var/www/cnf-back-office && mkdir -p .data && INTEGRITY_LOG=/var/log/cnf/integrity.log INTEGRITY_STATUS_FILE=/var/www/cnf-back-office/.data/integrity-status.json ./node_modules/.bin/tsx scripts/integrity-check.ts --quiet >> /var/log/cnf/integrity-cron.log 2>&1
  ```

- **`MAILTO`** must be a mailbox someone reads. A cron job whose failure mail bounces is
  a job that does not exist.

Verify the schedule is live:

```bash
sudo crontab -u cnf -l
grep CRON /var/log/syslog | tail -20
```

## 3. The weekly integrity check

### What it asserts

`scripts/integrity-check.ts` re-derives the money truths from the stored rows — the
application enforces them on every write, the database enforces what it can as
constraints, and this is the third line that catches whatever slipped past both
(plan.md §16, ADR 0004 §7). It **reads only**; it never repairs anything.

Nine checks. Seven fail the run, two are warn-only:

| # | Check                 | Assertion                                                                  |
| - | --------------------- | -------------------------------------------------------------------------- |
| 1 | Advance invariant     | per client, Σ `advances.amount` − Σ `advance_adjustments.amount` ≥ 0 (§8.4)  |
| 2 | Bill totals           | every bill: `net_payable = subtotal − deduction_total`                       |
| 3 | Adjustment rows       | every issued `ADVANCE_ADJUSTMENT` bill line has ≥ 1 `advance_adjustments` row |
| 4 | Totals vs lines       | stored `subtotal`/`deduction_total` equal the sums of the bill's own lines    |
| 5 | Receipt allocations   | per receipt, Σ `receipt_allocations.amount` ≤ `receipts.amount`               |
| 6 | Bill allocations      | per bill, Σ `receipt_allocations.amount` ≤ `net_payable` (§6.5)               |
| 7 | Orphaned adjustments  | no `advance_adjustments` row survives on a CANCELLED bill (ADR 0004 §4)       |
| — | Adjustment amounts    | *warn only* — `advance_adjustments.amount > 0` (CHECK-constraint backstop)    |
| — | Bill amounts          | *warn only* — bill money columns are not negative                            |

The two warn-only checks report but never fail the run. A negative `net_payable` is
legitimate when a client's advance adjustment exceeds the bill's charges, and a
non-positive adjustment amount means the CHECK constraint is missing from this database
rather than that money moved wrongly. Both are worth an eyeball, neither is an incident.

### Running it by hand

```bash
cd /var/www/cnf-back-office
pnpm db:integrity                     # full output, writes .data/integrity-status.json
pnpm db:integrity --quiet             # breaches only
pnpm db:integrity --help              # all options
pnpm db:integrity --status-file none  # do not touch the dashboard's status file
```

| Option / env var                            | Effect                                                        |
| ------------------------------------------- | ------------------------------------------------------------- |
| `--log <path>` / `INTEGRITY_LOG`            | Append one timestamped result line per run. Default: no log.   |
| `--status-file <path>` / `INTEGRITY_STATUS_FILE` | Where the dashboard status JSON is written. `none` disables it. Default `.data/integrity-status.json`. |
| `--quiet`                                   | Suppress the per-check PASS lines. Breaches are still printed. |

Exit codes: **0** = every check passed. **1** = a check failed, *or* the job could not
run (no database URL, database unreachable), *or* the result could not be recorded.
Anything non-zero deserves attention.

> **Never add this job to CI or to `pnpm build`.** It needs a real, populated database;
> an empty CI database would make it green for the wrong reason (plan.md §16).

**"The database is unreachable" but MySQL is clearly running.** The application's
connection pool gives up after 10 seconds. If MySQL is saturated — a long export, a
restore drill, a backup dump all at once — the job reports this rather than a breach.
Confirm before treating it as an incident, then simply re-run:

```bash
mysql -e "SHOW STATUS LIKE 'Threads_connected'; SELECT @@max_connections;"
```

The status file will already say `FAIL` with the check name `Integrity job`, which is
correct: the week's check genuinely did not happen. Re-running it clears the file.

### The log file

`INTEGRITY_LOG` appends exactly one line per run, whatever the result:

```
2026-08-16T11:24:35.718Z PASS 9 check(s), 0 failure(s), 51 warning row(s), 0.1s
2026-08-17T11:25:24.496Z FAIL 9 check(s), 2 failure(s), 0 warning row(s), 0.2s — Bill totals: bill 900001, bill 900002; Totals vs lines: bill 900001, bill 900002
```

Timestamps are UTC (ISO-8601, `Z`) so log lines sort and compare without ambiguity;
02:30 Dhaka is 20:30 UTC the previous day. The trailing detail lists the offending row
ids, capped at 20 per check with `+N more` — the full list is in the run output
(`/var/log/cnf/integrity-cron.log`) and in the status file.

One line a week is tiny, but rotate it anyway so it is never unbounded. `/etc/logrotate.d/cnf`:

```
/var/log/cnf/*.log {
    monthly
    rotate 24
    size 10M
    compress
    delaycompress
    missingok
    notifempty
    create 0640 cnf cnf
    su cnf cnf
}
```

Quick history:

```bash
grep FAIL /var/log/cnf/integrity.log        # every bad week, ever
tail -5 /var/log/cnf/integrity.log          # the last five runs
```

### The status file (how the Admin dashboard sees this)

The script never touches the application. Its only contract with the dashboard is a JSON
file, written atomically (temp file + `rename`) so a read never catches it half-written:

```json
{
  "lastRun": "2026-08-17T11:25:24.338Z",
  "status": "FAIL",
  "findings": [
    { "check": "Bill totals", "message": "bill 900001 (2026-42): subtotal 1,000.00 − deductions 100.00 = 900.00, but net_payable is 950.00" }
  ],
  "warnings": [
    { "check": "Bill amounts", "message": "bill 51 (2026-17): subtotal 0.00, deductions 10,000.00, net payable -10,000.00" }
  ],
  "checkedAt": "2026-08-17T11:25:24.496Z",
  "durationSeconds": 0.2
}
```

| Field             | Meaning                                                                     |
| ----------------- | --------------------------------------------------------------------------- |
| `lastRun`         | ISO-8601 UTC — when the run **started**.                                     |
| `status`          | `"PASS"` or `"FAIL"`. `FAIL` = at least one failing check, or the job could not run at all. |
| `findings`        | Breaches, one entry per offending row, `{ check, message }`. Empty on PASS.   |
| `warnings`        | Warn-only observations, same shape. Present on a PASS run; informational.     |
| `checkedAt`       | ISO-8601 UTC — when this file was written (end of the run).                  |
| `durationSeconds` | How long the checks took.                                                    |

Rules for whoever reads it:

- **Findings are capped at 50 rows per check.** When more exist, a final entry for that
  check reads `…and N more offending row(s) — see the run log for the full list.`
- **A missing file means the job has never run here** — show "not yet run", not "PASS".
- **Treat a stale file as an alarm.** The job runs weekly; if `lastRun` is more than
  ~9 days old, the schedule itself has stopped and that is as serious as a FAIL. The
  dashboard should say so.
- **A run that cannot start still writes the file**, with `status: "FAIL"` and one
  finding under the check name `Integrity job` (for example "the database is
  unreachable"). A check that silently stops running looks exactly like a check that
  keeps passing; this is what tells the two apart.
- The file is never read by the checks themselves, so deleting it is harmless — the next
  run recreates it.

Read it from the shell:

```bash
jq -r '"\(.status) — last run \(.lastRun), \(.findings | length) finding(s)"' \
  /var/www/cnf-back-office/.data/integrity-status.json

jq -r '.findings[] | "\(.check): \(.message)"' \
  /var/www/cnf-back-office/.data/integrity-status.json
```

The Admin dashboard shows the last result — status, when it ran, and the findings —
so the owner does not have to read a log file to know the books are consistent.

## 4. What to do when the integrity check FAILS

A FAIL means the stored data contradicts a rule the whole system is built on. It is an
incident for a human, not something to script around.

1. **Do not repair rows by hand in SQL, and do not re-run the job hoping it clears.**
   The check reads; it never repairs. Neither should you, until you know what happened.
2. **Stop issuing bills** until the cause is understood (plan.md §16). Tell the owner.
3. **Preserve the evidence — take a backup immediately**, before anyone changes anything:

   ```bash
   cd /var/www/cnf-back-office
   bash scripts/backup.sh --no-offsite --label pre-incident
   ```

4. **Read the findings.** `jq -r '.findings[] | "\(.check): \(.message)"' .data/integrity-status.json`,
   or the full run output in `/var/log/cnf/integrity-cron.log`. Each message names the
   offending row and states what it should have been.
5. **Find out when it started.** `grep FAIL /var/log/cnf/integrity.log` — the first FAIL
   line brackets the week the corruption appeared, which narrows the audit trail.
6. **Trace it in `audit_log`.** Every financial mutation writes a row (plan.md §6.6), so
   the offending bill or receipt id from step 4 leads to who changed what, and when.
   The table is append-only at the engine level (P7-F04 triggers, migration
   `20260816130000_audit_log_append_only`): an UPDATE or DELETE is refused with
   SQLSTATE 45000 — which is also what the integrity job's "Audit log append-only"
   check asserts. If that check FAILs, the triggers have been dropped and the
   audit trail is editable again: restore them from the migration immediately.
7. **Consult the rule that broke:** advance invariant → `docs/adr/0004-advance-engine.md`
   and plan.md §8.4; bill totals or lines → `docs/adr/0003-bill-line-model.md`;
   allocations → plan.md §6.5.
8. **If data was lost rather than merely wrong, restore into a scratch schema first** —
   never straight over the live database:

   ```bash
   bash scripts/restore.sh --list
   bash scripts/restore.sh --latest --target-db cnf_restore_check --skip-uploads
   ```

   Compare, decide, and only then restore for real. Full procedure: `docs/backup.md`.
9. **Re-run the check** once the cause is fixed, and confirm the dashboard goes green:

   ```bash
   pnpm db:integrity
   ```

10. **Contact.** Owner: TAMANNA TRADERS (proprietor). Technical: the developer
    contact recorded in `docs/deployment.md`. Fill both in before go-live — a runbook
    with a blank phone number fails at 3 a.m.

**Warn-only lines (`WARN`) do not fail the run** and do not need any of the above. Note
them, mention them at the next review, carry on.

## 5. The nightly backup

`scripts/backup.sh` is the **source of truth** for what the backup does — schedule,
contents, retention, off-server copy and every environment variable are documented in
its header and in `scripts/lib/backup-common.sh`. This section only covers scheduling it.

```cron
CRON_TZ=Asia/Dhaka
0 2 * * *  cd /var/www/cnf-back-office && bash scripts/backup.sh >> /var/log/cnf/backup.log 2>&1
```

- **02:00 Asia/Dhaka nightly**, gzipped `mysqldump` plus the uploads directory,
  **30 daily + 12 monthly** sets retained, and an off-server copy every night
  (plan.md §16). *A backup that lives only on the VPS is not a backup.*
- **Exit codes:** `0` success · `1` the backup failed, no usable set was produced ·
  `3` the local set is good but the off-server copy failed. **Treat 3 as an incident:**
  you have a backup, but only on the machine that is going to be the thing that fails.
- **Before every schema migration**, by hand, no exceptions (plan.md §15):

  ```bash
  bash scripts/backup.sh --no-offsite --label pre-migrate
  pnpm prisma migrate deploy
  ```

- **Restore** is `scripts/restore.sh` (`--list`, `--latest`, `--target-db`). It verifies
  `SHA256SUMS` before it touches anything and refuses a non-empty target without
  `--force`. The measured restore-drill time is recorded in `docs/backup.md`; the drill
  must actually be performed before go-live, not merely written down.

Check on it:

```bash
tail -30 /var/log/cnf/backup.log
ls -lh /var/backups/cnf-back-office/daily | tail -5
bash scripts/backup.sh --dry-run          # what tonight's run would do, changes nothing
```

## 6. Monthly five-minute review

Cheap, and it catches the failure mode where a scheduled job quietly stopped months ago:

```bash
tail -5 /var/log/cnf/integrity.log                      # weekly PASS lines, uninterrupted?
jq -r .lastRun /var/www/cnf-back-office/.data/integrity-status.json   # within 9 days?
ls -lh /var/backups/cnf-back-office/daily | tail -3     # last night's set is there and non-trivial?
ls -lh /var/backups/cnf-back-office/monthly | tail -3   # a set for this month?
sudo crontab -u cnf -l                                  # both lines still installed?
```

Once a year, do a real restore drill and update the measured time in `docs/backup.md`.
An untested backup is a hope, not a plan.
