# Query plans — the index drill

**Owner:** DB Engineer · **Task:** P7-T002 · **Plan reference:** `plan.md` §9.2

Reports are the hot path. This page records what MySQL 8 actually decides to do with
every report query when the database holds a realistic amount of trading, and it is
regenerated from a live `EXPLAIN` rather than written from memory.

## How to reproduce

```bash
pnpm tsx scripts/explain-check.ts              # verify — exit 0 when clean
pnpm tsx scripts/explain-check.ts --write-doc  # verify and rewrite this page
pnpm tsx scripts/explain-check.ts --reseed     # rebuild the dataset first
```

The drill runs against a dedicated `cnf_volume` schema built from the same
migrations — never `cnf_dev` (the owner's real development data) and never
`cnf_test` (the Playwright suite resets it between runs). One-time creation:

```bash
mysql -u root -e "CREATE DATABASE cnf_volume CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"
mysql -u root -e "GRANT ALL PRIVILEGES ON cnf_volume.* TO 'cnf_migrate'@'127.0.0.1'; FLUSH PRIVILEGES;"
DATABASE_URL="mysql://cnf_migrate:PASSWORD@127.0.0.1:3307/cnf_volume" pnpm exec prisma migrate deploy
```

`scripts/seed-volume.ts` then fills it (automatically, on the drill's first run) from a
fixed PRNG seed, so two runs on two machines produce identical rows and a changed plan
can only be explained by a changed index.

## Indexes this drill added

The first run of the drill found three full table scans, all of them in
`getDashboardOverview`'s all-time position figures. Migration
`20260816120000_report_covering_indexes` fixes all three by widening an existing index
into a **covering** one — no query was rewritten, because an index cannot change an
answer and the reports are already tested.

| Was | Now | Fixes |
|---|---|---|
| `bills(status)` | `bills(status, subtotal)` | `SUM(subtotal) … WHERE status IN (…)` — was `ALL` over 5,078 rows, now a covering `range` |
| `advance_adjustments(bill_id)` | `advance_adjustments(bill_id, amount)` | `SUM(amount)` all-time and the per-bill correlated sums — was `ALL`, now covering |
| `expenses(channel_id)` | `expenses(channel_id, amount)` | `SUM(amount)` all-time and per channel — was `ALL` over 19,423 rows, now covering |

Each old index is a strict leftmost prefix of its replacement, so nothing lost an access
path. The migration creates the wider index before dropping the narrower one, because two
of the three back a foreign key and MySQL will not drop the last usable index for one.

## An observation that is not an index problem

`R5 Advance Ledger — as-of date, consolidated` sends **43** statements for 40 clients.
`getAdvanceLedger` calls `getOutstandingBalance(clientId, asOf)` in a sequential
`await` loop, one round trip per client, so the count grows linearly with the client
list. Every one of those statements is index-backed — that is why the drill passes — but
at 200 clients it is 200 sequential round trips for one report. Fixing it means changing
the query shape in `report.service.ts`, which is the Backend Engineer's file, not the
DB Engineer's; recorded here so it is not lost.

## Reading the access types

| `access_type` | Meaning |
|---|---|
| `const` / `eq_ref` | One row, by primary or unique key. The best possible. |
| `ref` | Index lookup on a non-unique key — the normal shape for `client_id`, `job_id`, `category_id`. |
| `range` | Index range scan — the normal shape for a `bill_date` / `expense_date` window. |
| `index` | Full scan of the index rather than the table. Acceptable: it reads the smaller structure and stays in the buffer pool. |
| `ALL` | **Full table scan. This is the failure.** |
